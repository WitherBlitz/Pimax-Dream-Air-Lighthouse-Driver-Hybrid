## Evidence for the new source

After returning to stock Pimax rendering, the user reports perfect tracking and no stutter, but prefers the previous custom optics. The .4 Pimax profile obtains poses directly from its own PVR FloorLevel session and keeps the inherited custom renderer. It does not use the .3 alignment bridge.

A read-only comparison produced **250/250 fully valid pairs**. Selecting FloorLevel on a new PVR session without recentering matched stock raw positions within **0.25 mm per axis** in a mostly stationary capture. Both reported universe **31**. The EyeLevel default had a vertical offset. These measurements support using FloorLevel and the runtime-reported universe; they do not establish moving-head visual stability. The installed System32 PVR client reports SDK 1.33.1. The user's working stock state and exact old optics were backed up before installation.

The user reports stable translation and rotation in the Pimax lobby but severe jitter/loss in SteamVR. The restored station setup remains A/b with a sync cable. `forceTracking=true` eliminates gray screens but can make an invalid or frozen pose appear valid.

A simultaneous 30-second read-only comparison returned **1,916/1,916 Pimax poses with both position and orientation flags**, using Pimax tracking style 2 (Lighthouse). Pimax position/orientation changed while SteamVR's forced-valid HMD output stayed frozen; the original source callback count did not advance. This demonstrates separate software pose behavior in that session. It does not prove every earlier failure has the same cause or establish controller behavior.

The installed Valve receiver console identified both A/B stations, received hits on all 28 configured sensors, reported roughly 1,000 Hz IMU and ongoing optical packets, and decoded SensorType 9. The headset device configuration matched SteamVR's cached configuration field-for-field. These were read-only checks; no firmware, optical geometry, calibration database or station changes were made by this update. Investigation now focuses on the software path; no hardware defect is asserted.

## Completed software checks

- The user confirmed .5 motion works perfectly and requested preservation. The complete .5 release, corresponding source, full Git history bundle, installed DLL and live settings were copied to a separate timestamped snapshot before alignment changes.
- Read-only .5 captures identified PVR FloorLevel universe 31 and Lighthouse universe 1784100291 with identical station/controller serials. The controllers differed by approximately two metres. Matching the primary station's full pose gave a rigid mapping with controller residuals 7.4/10.7 mm and orientation residuals under one degree. Using the secondary instead left approximately 194 mm controller errors. The .6 change therefore maps only Lighthouse world transforms from the serial-matched primary; native HMD optics, tracking and prediction stay unchanged.
- A single rigid transform cannot reconcile the differently saved secondary-station calibration: its model remains approximately 214 mm and 5.43 degrees from the PVR-reported pose. No station calibration is rewritten or averaged. Primary/source validity, early callbacks, full model/world offsets, frame and universe changes, loss/reset, malformed data, ambiguous references and HMD isolation have regression coverage. The user subsequently confirmed working .6 native headset and Lighthouse controller tracking.

- The user confirmed the saved optics were restored, then reported disconnected/delayed head turns. A 20-second moving capture had 1,285 valid PVR/OpenVR samples, zero missed/dropped compositor frames and maximum compositor GPU time 1.8 ms. Rotational velocity did not follow FloorLevel orientation: inverse room-yaw mapping reduced derivative error from roughly 1.85 to 0.033 rad/s. Measured SteamVR prediction applies the submitted angular vector in body space, requiring an additional inverse pose rotation. Linear velocity was already in FloorLevel world space and is preserved. New regressions reproduced both missing mappings; corresponding correction is in .5. Live confirmation of the prediction correction is recorded separately.

- Live .4 testing loaded the exact saved distortion profile and System32 PVR client. With SteamVR's default single-driver setting, Lighthouse did not load and native head poses were invalid. Enabling `activateMultipleDrivers` loaded Lighthouse and restored genuine native pose validity, while suppressing the duplicate Dream Air HMD. A sandbox regression reproduced the missing setting before the installer correction. The user then confirmed: old optics restored, tracking still good. Extended game and reconnect behavior remain unverified.

- New runtime mapping tests cover timing, position, orientation, velocities, partial flags, nonfinite data, API failure, stale/future timestamps, disconnect and finite held references. Headset identity tests exclude controllers, unrelated headsets and the native runtime HMD from duplicate suppression.
- Independent review identified backend mismatch, suppression before original class restoration, missing disconnection publication and the native profile's multiple-driver requirement. These were corrected before packaging. Seven profile cases preserve optics and force flags. Nine installer cases include rejection of Play/private-only Pimax mode and refusal to activate native poses without the required runtime setting.

- New bridge regressions first failed against a scaffold, then passed. Review timing regressions reproduced mismatched represented timestamps, omitted submission latency and stale native acceptance (15/18 before correction). Steady-window/motion regressions also failed before implementation. Final aggregate: **22/22 native pose, 41/41 existing pose, 50/50 floor, 11/11 launcher, 3/3 isolated elevation-host and 5/5 profile cases**.
- Native coverage includes noncommuting rotations and rotated head offsets, matching-pose timing, delayed submissions, genuine validity before force flags, finite invalid fallback, continuity after Lighthouse callbacks stop, consistent low-motion alignment, source changes, lifecycle and controller exclusion. Both native and forwarded Lighthouse offsets are rebased through serialized submission.
- Independent read-only review found timing and test-coverage defects, reproduced with focused regressions and corrected. The review does not judge live improvement or PVR coordinate stability across recenter/reconnect; restart SteamVR to rebuild alignment after such changes.
- **7/7 installer cases** passed with actual driver payloads in isolated marked sandboxes, including selected Pimax profile, force preservation, settings/distortion preservation, malformed input rejection and byte-exact rollback. Profile preservation also passed **5/5 in Windows PowerShell 5.1**. Installer and long-path shell results are recorded in the verification ledger.
- Builds use Release x64, MSVC v145 and `SkipPostBuild=true`; inherited upstream conversion warnings remain. The bundled official GUI/private helper are unchanged. Source/package checks are completed before delivery.

## Validation boundaries

The user confirmed .5 moving-head behavior after its prediction correction. The .6 alignment update is validated separately against live runtime coordinates and user feedback. Unit/sandbox checks do not establish Gorilla Tag stability, complete feature parity or proprietary PVR behavior. Earlier bridge results remain historical coverage rather than validation of the current path.

The earlier .2 driver was installed and tested; its original Lighthouse path still showed invalid/frozen callbacks in the resumed session. The .2 guard correction remains included: chronological history uses callback arrival, while valid predictor fields retain their relative offsets. Baseline statistics continue updating.

Floor apply/restore is unchanged and remains unverified against the real chaperone service. Its **50/50** tests use simulated runtime behavior and real durable backup files; read-only height measurement worked. Floor writes refuse both force flags. Profiles now preserve those flags as requested, so forced-valid runtime output must not be presented as genuine source health.

Inherited upstream shutdown/API/hook cleanup behavior and private-helper internals remain outside this change. The optional native mode changes the Dream Air HMD pose route and maps Lighthouse device world transforms into its coordinate space. Keep the installer backup for rollback.
