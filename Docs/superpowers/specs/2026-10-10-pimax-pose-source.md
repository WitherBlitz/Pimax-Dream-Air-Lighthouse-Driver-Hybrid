# Pimax pose source for Dream Air

The user wants the Dream Air to retain sboys3 rendering and headset features, a Windows launcher, Lighthouse 1.0 A/b cable support, fixed custom floor height, and forceTracking=true. Stable tracking in the Pimax lobby includes position and rotation. A simultaneous 30-second API capture returned 1,916/1,916 Pimax poses with both tracking flags, while SteamVR's forced-valid headset pose stayed frozen and its source callback count did not advance. The selected software experiment is an optional Pimax headset pose source in the existing Lighthouse shim.

Keep the default source Lighthouse for compatibility. Add the Pimax profile to the release launcher; it selects the new source with the guard disabled, preserving existing force flags. Existing profiles select Lighthouse. Profile/install actions must retain explicit force settings. The new mode uses the installed Pimax API, without firmware changes or proprietary component modifications.

Register only an activated Dream Air HMD. Capture its original Lighthouse pose and owning server-host callback before force flags or filtering. Once a genuinely valid, connected, finite Lighthouse pose and a genuinely valid Pimax pose are delivered within 50 ms and describing instants within 20 ms, require a consistent 150 ms low-motion window and derive one rigid transform from Pimax coordinates to the headset's existing SteamVR world. Include the original driver/world and head-reference transforms. Keep that transform fixed for the session. Do not calibrate from forced validity or an old pose. Until alignment succeeds, keep the original path and expose waiting status.

Poll Pimax tracking in the existing active headset RunFrame. Publish the converted head pose through the captured Lighthouse owning host and original callback; suppress competing Lighthouse HMD submissions after alignment. Serialize both paths. Keep controller inputs and poses unchanged. Clear alignment on activation/deactivation or source change. Reject nonfinite, invalid, disconnected, or excessively old/future Pimax samples; expose the original Pimax validity before the user's force setting is applied. Preserve the existing room universe and chaperone so floor tools continue using the same standing origin. This does not fix independently unstable controller poses.

Diagnostics must show selected source, alignment state, original Lighthouse counts/validity and Pimax counts/validity, plus the usual output statistics. Runtime output marked valid by forceTracking is not evidence of healthy tracking.

Verification: failing then passing math/state regressions for nonidentity transforms, invalid/forced calibration, stale pairing, continuity after Lighthouse loss, native invalid/NaN handling, source toggles and device lifecycle; profile preservation and launcher selection tests; full existing build/tests. Install only while SteamVR is stopped, with backups. Restart with Pimax profile and forceTracking preserved. Require fresh diagnostics and compare Pimax/API motion with SteamVR output; do not claim improved hardware tracking from unit tests. A waiting alignment or controller mismatch must be reported explicitly.
